## 1. 背景与目标

**谁的问题**：铜加工、镀锌板、有色冶炼等实体企业存在真实的价格波动风险，需要利用境内
期货/期权市场做套期保值，但缺少期货专业团队——套保比率算不出、套期会计文档写不来、
交易所额度与证监会持仓监管的底线摸不清。

**解决什么问题**：

1. **合规门槛降不下来**——套期关系必须**正式指定**、必须有**书面文件**载明有效性评估方法；
   企业自行用 Excel 管理时，实货敞口与期货交易之间没有可信追溯链。
2. **正当性无法自证**——交易所对"使用套保额度频繁开平仓且无法说明正当理由"可采取
   限制开仓、限期平仓乃至强行平仓；企业拿不出证据。
3. **风控与核算脱节**——金融衍生业务盈亏与实货盈亏本应综合评判，但两侧数据在不同表里，
   无法同屏对账。
4. **多业务线资金/持仓混在一起**——企业需要在同一个真实期货账户内按业务线拆分管理，
   但 CTP 标准报单接口不提供子账户字段，拆分只能靠系统自行记账。

**本系统做什么**：按 **`PROJECT.md` §1** 定义的"敞口 → 方案 → 交易 → 会计"合规闭环，
提供 9 个业务模块 + 2 个支撑模块，之上叠加**贯穿性子账户体系**，
使每一笔期货交易都能追溯到它所对冲的实货敞口、所依据的套保方案与可自证的正当理由。

**成功如何衡量**：以 **`PROJECT.md` §10 的 37 条成功标准**为唯一验收依据，本需求文档集
的每条 FR/NFR 均可映射到其中至少一条（映射关系见各模块文件的「验收标准」与
`NONFUNCTIONAL.md` 的「验证方式」）。

**合规基准**：按**国资委 8 号文（国资发财评规〔2020〕8号）+ 17 号文（国资厅发财评〔2021〕17号）**
设计（**按央企标准设计，不宣称"满足央企合规"**，见 `PROJECT.md` §4.1.F）。

**架构总览（需求视角）**：本系统为**双组件**——**C++ 交易组件**（CTP 对接、下单、
事前风控、指令流水与重放，**完全不访问数据库**）与 **Java 业务组件**（其余全部模块、
内置 HTTP Server 托管前端、经**标准 JDBC** 访问达梦 DM8）；两组件经**本地 TCP 回环双向通信**。

### 2.1 子账户贯穿字段规范（⚠️ 全项目红线）

> **依据**：`PROJECT.md` §4.1.B「子账户体系」+ §4.1.C「各模块的子账户影响」+
> §6 约束行「子账户体系」+ §4.1.E（三）「编码约定」。
>
> **规范原文**：每张业务表凡涉及**资金、持仓、交易、敞口、凭证**者，
> **必须显式携带子账户标识**，**不得依赖"通过关联表间接推导"**。

**本规范是 S2 `DATA_MODEL.md` 的强制输入**，也是 M1 门禁（数据模型三方会签）中
**产品经理席位的核心审查项**。

| # | 数据类别 | 必须显式携带子账户标识的业务对象 | 所属模块 | 业务含义（为何必须要） |
|---|---------|--------------------------------|---------|---------------------|
| 1 | **敞口** | 采购合同/订单、销售合同/订单、生产计划/在制品、库存台账、**实货敞口** | `SPOT`、`PRODUCT` | 实货敞口是 17 号文"期现一体"的**根**；敞口不归属子账户，就无法按子账户做规模红线与净持仓校验 |
| 2 | **计划** | 套保计划、交易计划、套期关系书面文件 | `PLAN` | 计划是交易正当性的依据；计划不绑子账户，交易就无法证明属于哪条业务线 |
| 3 | **交易** | 交易指令、委托、成交记录、事前风控拒绝记录、交易理由记录 | `TRADE`、`RISK` | 每笔单必须可定位到子账户，否则事前风控无法按子账户维度校验额度与持仓上限 |
| 4 | **持仓** | 持仓明细、持仓汇总、结算持仓、保证金占用 | `TRADE`、`SETTLE`、`FUND` | 期货公司侧持仓是合并的，拆分完全依赖系统记账；缺标识则**加总对账**必然失败 |
| 5 | **资金** | 资金台账、资金流水（期初/出入金/调拨/盈亏结转/手续费/保证金变动/期末）、资金额度 | `FUND`、`SETTLE` | 各子账户资金独立；缺标识则既无法划拨，也无法校验"划拨后加总不变" |
| 6 | **凭证** | 会计凭证（草稿与正式）、有效性评估记录、再平衡记录 | `ACCT`、`AUDIT` | 凭证须可按子账户出账；审计追溯链须包含子账户维度 |

> **脚注（源自变更 `CH-003`）**：**现货价格记录不属于上表"敞口类必带"清单**。
> 现货价是**全账户共享的市场数据（单价）**：唯一口径 = `品种 + 日期 + 来源标注`（**不含子账户维度**）；
> 其行内 `sub_account_id` 语义为**录入归属**，**不参与业务归属判定，也不参与加总**
> （`Σ 子账户 = 真实账户` 的加总仅适用于**资金 / 持仓 / 结算**三类数据）。

**五类红线（可用于 M1 门禁逐条核对）**：

1. **资金** 类数据携带子账户标识 ✔
2. **持仓** 类数据携带子账户标识 ✔
3. **交易** 类数据携带子账户标识 ✔
4. **敞口** 类数据携带子账户标识 ✔（**不含现货价**——现货价见上表脚注，`CH-003`）
5. **凭证** 类数据携带子账户标识 ✔

**配套约束**：

- **不得**用"用户 → 子账户"或"计划 → 子账户"的关联推导替代**数据行自身**的子账户标识
- `AUTH` 模块的用户-子账户授权关系**不属于**上述五类，它是**权限维度**而非业务数据维度，
  但仍须登记（见 `AUTH.md`）
- **加总对账要求**：资金、持仓、结算三类数据的子账户标识必须使其**可直接求和**，
  以支持 `Σ 子账户 = 真实期货账户`（`SETTLE` 模块 P0 需求）
- 子账户为**逻辑虚拟账户**，**不是**期货公司侧的分户；CTP 报文中**不存在**该字段，
  故该标识**只能由系统自行记账维护**，不得假设可从 CTP 回报中取得

### 2.2 模块关系图

> 说清模块间的**依赖方向**与**数据流向**。这是架构分层的上游输入。

**主数据流（期现一体，⚠️ 单向：从实货敞口出发）**：

```
 ⑪ CONFIG ──配置──→ 全部模块
 ⑩ AUTH   ──授权/数据可见性──→ 全部模块

 ① PRODUCT ──品种白名单/额度指标──→ ② SPOT
                                     │
                          ② SPOT ──实货敞口（根）──→ ③ PLAN
                                                      │
                                            ③ PLAN ──交易计划──→ ④ TRADE
                                                                  │
                            ④ TRADE ──事件流（成交/持仓/拒绝）──→ ⑤ SETTLE
                                                                  │
                            ④ TRADE ──事件流──→ ⑥ RISK（事中/事后）
                                                                  │
                            ⑤ SETTLE ──结算结果──→ ⑧ ACCT ──凭证──→ ⑦ AUDIT
                            ⑨ FUND  ──资金流水/凭证──────────────────→ ⑦ AUDIT

 ④ TRADE ⇄ C++ 交易组件（事前风控在 C++ 内全内存执行，⑥ RISK 承载）
```

**依赖方向说明（架构分层依据）**：

| 关系 | 方向 | 说明 |
|------|------|------|
| `PRODUCT` → `SPOT`/`PLAN`/`TRADE`/`RISK` | 上游 | 品种白名单与额度指标是全链路校验的基准数据 |
| `SPOT` → `PLAN` | 上游（**不可逆**） | **实货敞口是根**；禁止"先有期货成交再反找现货"（17 号文） |
| `PLAN` → `TRADE` | 上游 | 每笔交易必须绑定计划 ID 与实货敞口 ID |
| `TRADE` → `RISK` | 上游（事件流） | `RISK` 事中风控基于 `TRADE` 推送的事件流构建镜像状态 |
| `TRADE` → `SETTLE` → `ACCT` | 上游 | 结算 → 会计凭证 |
| `ACCT`/`SETTLE`/`FUND`/`RISK` → `AUDIT` | 上游 | 审计从各模块取数，**不反向写入**（只读 + 留痕） |
| `AUTH`/`CONFIG` | 横向 | 被全部模块依赖，不依赖任何业务模块 |

**组件归属视图**：

```
┌────────── C++ 交易组件（不访问数据库）──────────┐
│ ④ TRADE：CTP 对接、下单、指令流水与重放           │
│ ⑥ RISK：事前风控（全内存，三层限额校验）          │
│ ⑨ FUND：CTP 资金划转接口收发                      │
└────────────────────┬─────────────────────────────┘
                     │ 本地 TCP 回环（127.0.0.1 + 连接鉴权）
                     │ C++→Java：事件流  ／  Java→C++：控制指令
┌────────────────────▼─────────────────────────────┐
│ Java 业务组件（经标准 JDBC 访问达梦 DM8）          │
│ ①②③⑤⑥(事中/事后)⑦⑧⑨⑩⑪ + 内置 HTTP Server     │
└────────────────────┬─────────────────────────────┘
                     │ 静态托管（零构建链）
              ┌──────▼──────┐
              │ 前端 HTML/JS │
              └─────────────┘
```

### 2.3 模块拆分规则

> 触发条件：**单模块 FR 超过 20 条**。
>
> **默认动作是拆模块，不是拆文件**——模块太大的根因通常是模块边界划粗了。

| 情形 | 处理 |
|------|------|
| 单模块 FR ≤ 20 条 | 保持单文件 |
| 单模块 FR > 20 条 | **先拆模块**：识别子域 → 把成簇职责提成新模块 → 在 §2 登记新代号、建新模块文件 |
| 拆模块后仍 > 20 条 | 兜底：开二级文件 `<模块>-<子域>.md`，须在 §2 登记，追溯链注明子文件路径 |

**未触发拆分**，故**无二级文件**。

> ⚠️ **不要拿条数当尺子**：20 条是**拆模块的触发线**，不是粒度标准。
> 各模块大小本就不一样（`AUTH` 与 `TRADE` 体量不同是正常的），
> 判断粒度只看 `product-manager` 定义 §6.1 的三条检验。

## 3. 术语表

> ⚠️ **业务术语的唯一事实源。**
> 同一概念在**任何**需求文件中必须使用同一术语；下游角色（架构/任务/用例）

| 术语 | 英文 / 缩写 | 定义 | 使用范围 |
|------|------------|------|---------|
| **实货敞口** | — | 企业因现货经营（采购、销售、生产、库存）而暴露于价格波动风险的数量与方向。**是 17 号文「期现一体」的起点、全系统的数据源头**。默认口径 = **组合口径（含生产计划）**：已签合同未执行量 + 库存持有量 + 生产计划需求量，三类分量分别记录与展示（`Q-17`，源自变更 `CH-002`）。**唯一用词**，不同义于"现货敞口""敞口" | `SPOT`、`PLAN`、`TRADE`、`RISK`、`ACCT`、`AUDIT` |
| **套保计划** | — | 由实货敞口出发编制的、经审批的套期保值方案，含品种、方向、数量、期限、套保比率、对应实货敞口。**先于交易存在** | `PLAN`、`TRADE`、`RISK`、`AUDIT` |
| **交易计划** | — | 套保计划分解出的可执行下单任务（合约、方向、数量、期限）。一笔交易计划可对应多笔交易指令 | `PLAN`、`TRADE` |
| **子账户** | — | 系统内的**逻辑虚拟账户**，非期货公司侧真实分户。一个真实期货账户下可有多个子账户，各有独立资金、持仓、结算，相互可划拨。CTP 报文**不含**该字段，由系统自行记账维护 | 全部模块 |
| **真实期货账户** | — | 企业在期货公司开立的、实际持有资金与持仓的账户。**全系统只有一个**，是加总对账的基准 | `SETTLE`、`FUND`、`AUDIT` |
| **加总对账** | — | 每日结算的必做校验：**Σ 子账户数据 = 真实期货账户数据**。不一致须**全账户告警**并**仅阻断差异所属子账户**的新开仓 / 资金划拨 / 日终关账（**不阻断平仓、不波及其他子账户**），不得静默通过（`Q-11`，源自变更 `CH-001`） | `SETTLE`、`FUND`、`AUDIT` |
| **子账户划拨** | — | 子账户之间的资金调整，属**系统内记账调整**，真实期货账户资金**不变动**，划拨后加总金额不变。须审批与留痕 | `FUND`、`AUDIT` |
| **套保比率** | — | 套保数量相对实货敞口规模的比例。三档计算方法：简单比率法 / 最小方差法（`h = ρ × σ_S / σ_F`）/ 自定义规则法 | `PLAN`、`SPOT` |
| **事前风控** | Pre-trade Risk | 下单**前**的校验，在 **C++ 交易组件内全内存执行**，指令路径**零数据库 I/O**，不通过则**拒绝下单、不发往 CTP** | `RISK`、`TRADE` |
| **事中风控** | Intraday Risk | 交易**过程中**的实时监控，在 **Java 业务组件内**基于 C++ 事件流构建的**镜像状态**执行，可访问数据库 | `RISK` |
| **事后风控** | Post-trade Risk | 交易日**结束后**的风险计算与报表生成，在 Java 业务组件内**落库** | `RISK`、`AUDIT` |
| **镜像状态** | — | Java 侧根据 C++ 推送的事件流重建的实时持仓/资金状态，用于事中风控。**不是权威源**，权威源是 C++ 内存 | `RISK`、`TRADE` |
| **事件流** | — | C++ → Java 单向推送的数据流：成交回报、持仓变化、委托状态、事前风控拒绝记录。**同时**服务事中风控状态构建与数据落库 | `TRADE`、`RISK` |
| **控制指令** | — | Java → C++ 单向下发的指令：修改风控参数、更新品种白名单、调整额度、启停/重载、触发重放 | `RISK`、`CONFIG` |
| **指令流水与重放** | — | C++ 组件应对崩溃恢复的机制：在途指令落盘，启动时重放，防止重复计入或漏计导致超额下单 | `TRADE`、`RISK` |
| **规模红线** | — | 商品类年度保值规模 ≤ 实货经营规模 **90%**；贸易类 ≤ **80%**。**基数 = 年度现货敞口累计量（实物量口径）**，**按子账户与全账户双算取严者**；分类默认挂**子账户**并可**品种级覆盖**，比例可配置（`Q-1`/`Q-2`，源自变更 `CH-001`） | `RISK`、`PLAN` |
| **时点净持仓红线** | — | 任一交易时点，净持仓 ≤ 对应实货风险敞口；校验时点 = **下单瞬间（事前硬阻断）+ 日终复核（次日限制新开仓）**，敞口取**当日最新快照**并标注快照时点（`Q-3`，源自变更 `CH-001`） | `RISK`、`TRADE` |
| **期限红线** | — | 起算点 = **建仓日**；到期上限取「建仓日 + 12 个月」与「实货合同到期日 + 30 天宽限」的**较早者**；**禁止盲目展期**（`Q-4`，源自变更 `CH-001`） | `RISK`、`PLAN` |
| **套期关系书面文件** | — | CAS 24 法定留痕文件，含**正式指定 + 有效性评估方法 + 再平衡机制**三要素 | `PLAN`、`ACCT` |
| **有效性评估记录** | — | 按 CAS 24 定性有效性（关注**经济关系**）对套期关系持续评估的记录；触发再平衡时另出**再平衡记录** | `ACCT` |
| **六类风险** | — | ① 超额套保 ② 品种错配 ③ 期限错配 ④ 频繁开平仓 ⑤ 会计文档缺失 ⑥ 敏感信息泄露。**每类须对应一套机制** | `RISK`、`AUDIT` |
| **零落盘** | — | 敏感字段（密码、期货认证码 AuthCode、资金密码）**仅内存持有**，禁止写入任何持久化文件与日志；每次启动手工填写 | `CONFIG`、`AUTH`、`FUND` |
| **前中后台分离** | — | 8 号文硬要求：财务/风控岗、交易岗、结算岗三者不得由同一人担任；**严禁企业负责人直接操盘** | `AUTH` |
| **软隔离** | — | 子账户数据默认互不可见；**经授权角色**（管理层、审计岗）**可跨子账户查看** | `AUTH`、`SETTLE` |
| **双人复核** | — | 资金转账/划拨的发起人与审批人**不得为同一人** | `FUND` |
| **证据链** | — | 可导出的完整追溯链：`实货敞口 → 套保计划 → 审批 → 交易 → 结算 → 会计凭证` | `AUDIT`、`ACCT` |
| **套保效果** | — | 金融衍生业务盈亏与实货盈亏的**综合评判**；两者须**同时上报** | `ACCT`、`AUDIT` |
| **组件归属** | — | 该模块/需求由 **C++ 交易组件** / **Java 业务组件** / **前端**哪一侧承载 | 全部模块 |
| **现货价** | — | 现货价格，**只接受外部输入**（手工录入 / CSV 导入）；系统**不抓取、不订阅**任何第三方资讯源 | `SPOT`、`PLAN` |

**术语表维护纪律**：

- 一个概念**只有一个**术语，禁止同义词并存（如"实货敞口"与"现货敞口"必须二选一）
- 术语定义**不含实现细节**（不写字段名、表名、类型）
- 新增术语须回填本表；下游发现未登记术语，视为需求缺陷

>

| **财务/风控岗** | 负责实货敞口识别与套保计划编制；懂会计但非期货专业，使用频次每日 | 现货录入准确、敞口算得对、套保比率有依据、计划审批快 | 5.1 套保计划编制与审批、5.4 套期会计处理与有效性评估、FLOW-001 |

| **管理层/审批人** | 不直接操作，负责批准计划与额度；每周使用 | 一屏看清实货敞口、已套保比例、持仓、资金与额度使用情况 | 5.1 套保计划编制与审批、5.5 子账户资金划拨、5.6 全链路审计追溯与报表导出 |
| **审计/合规岗** | 内外部审计时提供证据链；按需使用，审计期密集 | 一键导出完整证据链；季度/年度报表；操作留痕不可篡改 | 5.6 全链路审计追溯与报表导出、FLOW-001 |
| **系统管理员** | 维护系统参数、CTP 连接、风险阈值、子账户与权限配置；按需使用 | 配置正确且可追溯、敏感字段不落盘、配置变更不影响在途交易 | 5.5 子账户资金划拨（配置支撑）、FLOW-001 |

> ⚠️ **岗位分离约束**（`PROJECT.md` §3，8 号文 四(一) 硬要求）：
> **财务/风控岗、交易岗、结算岗三者不得由同一人担任**；**严禁企业负责人直接操盘**。
> 系统权限模型须**强制**此约束，**不得**提供"超级管理员一键通办"的便利后门。
>
> ⚠️ **子账户数据权限**：上述角色均可被**限定到指定子账户**；默认子账户间数据不可见。
> **管理层与审计岗可被授予跨子账户查看权限**（软隔离，见 `PROJECT.md` §4.1.B）。
>
> ⚠️ **系统管理员不是业务角色**：其权限**不含**交易、审批、风控判定能力；
> 配置类操作须留痕并进入审计范围。

### 5.1 套保计划编制与审批

- **触发**：财务/风控岗识别到存在待套保的实货敞口（新签采购/销售合同、新增生产计划或库存变化）
- **参与者**：财务/风控岗、审批人、系统
- **前置条件**：品种已在 `PRODUCT` 建档并启用；现货合同与实货敞口已在 `SPOT` 录入并归属子账户；审批人已获授权（含品种与额度）
- **完成标志**：套保计划审批通过、状态生效，并已分解出交易计划

| 步 | 业务动作 | 执行者 | 涉及需求（可后补） |
|----|---------|--------|------------------|
| 1 | 查询待套保的实货敞口 | 财务/风控岗 | `FR-SPOT-15`、`FR-SPOT-16` |
| 2 | 选择套保比率计算方法（简单比率 / 最小方差 / 自定义规则） | 财务/风控岗 | `FR-PLAN-6`、`FR-PLAN-7`、`FR-PLAN-8` |
| 3 | 计算套保比率 | 系统 | `FR-PLAN-6`、`FR-PLAN-7`、`FR-PLAN-8` |
| 4 | 录入套保计划要素（品种、方向、数量、期限、子账户、对应实货敞口） | 财务/风控岗 | `FR-PLAN-1`、`FR-PLAN-19` |
| 5 | 生成套期关系书面文件 | 系统 | `FR-PLAN-9`、`FR-ACCT-1` |
| 6 | 提交套保计划审批 | 财务/风控岗 | `FR-PLAN-10` |
| 7 | 执行合规预校验（岗位权限、品种白名单、规模红线、期限红线） | 系统 | `FR-PLAN-10`、`R-PLAN-3`、`FR-RISK-4`、`FR-RISK-6` |
| 8 | 审批套保计划 | 审批人 | `FR-PLAN-11`、`FR-PLAN-12` |
| 9 | 计划生效并对交易端可用 | 系统 | `R-PLAN-1`、`FR-CONFIG-6` |
| 10 | 将套保计划分解为交易计划 | 财务/风控岗 | `FR-PLAN-14`、`FR-PLAN-15` |

**异常分支**：

| 编号 | 触发条件 | 处理方式 |
|------|---------|---------|
| 1 | 第 3 步最小方差法样本不足（现货价序列 < 30 个交易日） | **明确提示样本不足**，不静默降级；可改选其它方法或先补录现货价 |
| 2 | 第 4 步品种未启用或不在该子账户白名单内 | 中断，提示先启用品种或调整子账户白名单 |
| 3 | 第 7 步触及规模红线（商品类 90% / 贸易类 80%，基数 = 年度现货敞口累计量、子账户与全账户双算取严者）或期限红线（上限取「建仓日 + 12 个月」与「合同到期 + 30 天」较早者） | **阻断提交**，给出触及的规则编号与当前值/阈值（`Q-1`/`Q-4`，源自变更 `CH-001`） |
| 4 | 第 8 步审批驳回 | 计划回到草稿状态；**驳回原因必填**；回到第 4 步修改 |
| 5 | 第 5 步套期关系书面文件生成失败（关键要素缺失） | 中断并列出缺失要素；**不得**在无书面文件的情况下提交审批（对应"会计文档缺失"风险） |

**备注**：本流程体现 17 号文的**单向结构**——计划**由实货敞口出发**编制，
**不得**从期货成交记录反向创建计划。

### 5.2 套保交易执行（含人工确认与事前风控）

- **触发**：交易岗在交易时段着手执行已批准的交易计划
- **参与者**：交易岗、系统（C++ 交易组件 + Java 业务组件）
- **前置条件**：套保计划已生效并分解出交易计划；交易岗已获授权（人员名单、品种、额度齐备）；C++ 组件已完成事前风控参数全量预加载
- **完成标志**：成交回报已入链、额度占用已回写、交易理由已记录

| 步 | 业务动作 | 执行者 | 涉及需求（可后补） |
|----|---------|--------|------------------|
| 1 | 查看已批准的交易计划与实时可用额度（按子账户） | 交易岗 | `FR-PLAN-15`、`FR-PLAN-20`、`FR-FUND-15` |
| 2 | 确定合约与下单要素（方向、数量、价格、开平） | 交易岗 | `FR-TRADE-1`、`FR-TRADE-12` |
| 3 | 提交交易指令（绑定交易计划 ID、实货敞口 ID 与子账户标识） | 交易岗 | `FR-TRADE-1` |
| 4 | 执行事前风控校验（白名单、额度、持仓上限、期限、价格偏离、权限；**三层限额：子账户 + 品种 / 子账户 + 合约 / 账户 + 品种**） | 系统（C++） | `FR-TRADE-3`、`FR-RISK-1`～`FR-RISK-8`、`R-RISK-2` |
| 5 | 人工确认后发出指令 | 交易岗 | `FR-TRADE-2` |
| 6 | 指令发往 CTP 柜台 | 系统（C++） | `FR-TRADE-2` |
| 7 | 接收委托回报 | 系统（C++） | `FR-TRADE-4` |
| 8 | 接收成交回报 | 系统（C++） | `FR-TRADE-5` |
| 9 | 推送事件流至 Java 并落库 | 系统 | `FR-TRADE-14`、`R-TRADE-3` |
| 10 | 回写额度占用与交易计划执行进度 | 系统 | `FR-TRADE-11`、`FR-RISK-2` |
| 11 | 记录交易理由与正当性说明 | 交易岗 | `FR-TRADE-10`（结构化必填：关联类型 + 关联对象 + 时点说明） |
| 12 | 事中风控实时监控与告警 | 系统（Java） | `FR-RISK-12`～`FR-RISK-16` |

**异常分支**：

| 编号 | 触发条件 | 处理方式 |
|------|---------|---------|
| 1 | 第 4 步事前风控不通过 | **直接拒绝，不发送 CTP**；给出规则编号与拒绝原因；拒绝记录经事件流上报 Java 落库 |
| 2 | 第 5 步人工确认超时未确认 | 指令失效，不发出；须重新提交 |
| 3 | 第 4 步 C++ 组件刚重启、尚未完成重放 | 拒绝一切新指令，直到重放完成（防止在途指令被重复计入） |
| 4 | 第 6 步 CTP 连接不可用 | 指令进入待发队列或退回交易岗；**不得**静默丢弃 |
| 5 | 第 11 步交易理由未填写或关联对象缺失即离开 | 该笔交易在追溯链中标记，进入 `AUDIT` 违规筛查范围——**"理由缺失"与"关联缺失"为两个并列独立维度**；**提交路径**缺关联对象**拒单**，**补填态 / 异常态**（关联对象暂缺）须带**关联对象缺失标记**（条件非空）方可留存（`Q-13`，源自变更 `CH-002`，口径澄清见 `CH-004`） |

**备注**：本流程**不含自动交易**（`PROJECT.md` §4.2 明确排除）；"人工确认"本身

  前中后台岗位分离、严禁负责人直接操盘、转账双人复核、6 类风险各一套机制、
  敏感字段零落盘

**不包含**：见 §7。

## 7. 明确不做（Out of Scope）

> 与 `PROJECT.md` §4.2 **逐条对应**，本节不新增排除项、不删减排除项。

| 排除项 | 排除理由 | 后续处理 |
|--------|---------|---------|
| **投机/自营交易功能** | 上期所与上市公司指引均明确不得用"套期保值"用语掩盖投机；系统若允许投机则丧失全部合规价值 | **以后也不做**——这是定位问题，不是版本问题 |
| **多租户 SaaS** | 套保数据涉及企业核心经营数据与持仓，客户不可能接受托管；本系统为企业自部署自管理 | 以后如需，**另立项目** |
| **行情分析/预测/投研功能** | 本系统是套保执行与合规工具，不做"该不该套保"的市场判断；涉及投资建议需持牌 | **以后不做** |
| **自动交易** | 交易指令须由交易岗**人工确认后**发出；自动下单合规风险不可控，且"人工确认"本身是正当性证据环节 | 以后若要，须先取得交易所与内控**双重认可** |
| **第三方现货资讯源对接** | 引入付费依赖 + 账号管理 + 抓取合规风险，且各企业数据源不同无法统一 | 以后如需，由企业自行开发导入适配器 |
| **完整 ERP（采购审批、供应商、出入库作业、应收应付、生产排程）** | 与客户既有 ERP 重叠；本系统现货模块定位是"**为套保服务的现货视图**" | 以后如需深度集成，**另立适配器项目** |
| **移动端 App** | 套保操作场景在办公桌前，移动端无实际需求，且会拖慢 ④⑤ 进度 | 本期不做；**仅 Web（桌面浏览器）** |
| **境外/场外衍生品** | 17 号文要求优先选择境内交易场所、商品类原则上仅开展场内业务；场外需单独风险评估 | 以后如需，**须单独立项** |
| **与银行的企业侧直连（三方协议/前置机/银企直连）** | 银期划转的银行侧执行本属**期货公司**职责；CTP 已提供资金接口，复用即可 | **"不需要做"，不是"本期不做"** |
| **组件间 JNI 同进程部署** | 同进程需 JNI，复杂度陡增 | 维持**同机双进程**（`PROJECT.md` §5.3） |
| **C++ 组件访问数据库** | 事前风控在指令路径上须零 I/O；单一写库入口保证一致性 | **永久排除**（架构红线） |
| **前端构建链（npm/Vite/React/打包产物）** | 前端须与其他模块有效隔离、升级互不影响 | 维持**原生 HTML + vanilla JS，零构建链** |
| **数据库存储过程 / 触发器 / 自定义函数** | 保证数据库可更换性（`PROJECT.md` §5.2） | **永久排除**；业务逻辑放 Java 层 |
| **C++14/17+ 特性** | 严格 C++11（`PROJECT.md` §6） | **永久排除** |
