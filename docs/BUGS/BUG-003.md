## 复现步骤

> 最小可复现 = 部署脚本 4 个 M1 建表脚本 + 2 个子账户 + 同一品种/敞口，**两子账户在「同一业务日」各自编制一条套保计划**。

1. 建表（`docs/DEPLOY/schema/m1_{config_auth,product,spot,plan}.sql`）并建**两个子账户** A、B（`POST /api/v1/config/sub-account`）。
2. 为 A、B 各配置同一品种与一条实货敞口（`POST /api/v1/spot/exposure`）。
3. 令业务日为 `D`，为**子账户 A** 编制计划：`POST /api/v1/plan`（`subAccountId=A, …`）⇒ **200**，`plan_no = HP<D>0001`。
4. 仍为业务日 `D`，为**子账户 B** 编制计划：`POST /api/v1/plan`（`subAccountId=B, …`）⇒ **失败**（见「实际结果」）。

> 等价复现（本席固化用例，确定性、离线）：在 `java/` 下运行
> `TMPDIR=/root mvn -B -o -Punit -Dtest=M1EndToEndAcceptanceTest#acceptance1SameDayTwoSubAccountsPlanCreationIsBlockedByPlanNoCollision test`。
> 该用例的 `system-out` 即打印 `plan_no` 取值与第二个子账户的响应（见「证据」）。

## 期望结果

**两个子账户在**同一业务日**各自编制计划应各得成功**，且各自 `plan_no` 互异（全局唯一）。
**依据**：`DATA_MODEL.md:1661/:1687`（`plan_no` 全系统唯一 + `uk_hedge_plan_no UNIQUE(plan_no)`）；`DATA_MODEL.md:4368`（编号 `HP<yyyyMMdd><seq(4)>`）；`REQUIREMENTS/PLAN.md:34/:35`；`PROJECT.md:561`（M1 验收方式即要求两名子账户各自产出计划）。

## 实际结果

第二个子账户的编制请求**被拒**（HTTP `500` / 业务码 **`10022` 内部错误**），计划**未落库**；根因为**违反唯一约束 `uk_hedge_plan_no`**：

```
[T-024][BUG-003] plan_no：A=HP202609200001 ; A2=HP202609200002 ; B2 序号同 A2（均应 = HP<日><seq>，无子账户维度）
[T-024][BUG-003] 第二子账户 B2：status=500 code=10022 body={"code":10022,"message":"内部错误","traceId":"HG-T024"}
```

服务端日志（`ErrorMapper` 记录的根异常）：

```
java.lang.IllegalStateException: 事务内查询失败：SQLState=null；错误码=0；
  原因=违反唯一约束 uk_hedge_plan_no：t_hedge_plan(plan_no) 已存在相同取值，拒绝重复插入；复现=核对语句与该表约束（DATA_MODEL.md §2）
Caused by: java.sql.SQLException: 违反唯一约束 uk_hedge_plan_no：t_hedge_plan(plan_no) 已存在相同取值，拒绝重复插入
```

**根因链**：`com.hedgeguard.service.PlanService#createPlan`（`java/src/main/java/com/hedgeguard/service/PlanService.java:573`）：

```java
long seq = hedgePlanDao.count("sub_account_id = ?", Arrays.asList(plan.subAccountId)) + 1;  // ← 按【子账户】计数
plan.planNo = BizNoGenerator.hedgePlan(Clocks.today(), seq);                                  // ← HP<yyyyMMdd><seq> 无子账户维度
```

`count` 的过滤条件**只有 `sub_account_id = ?`**（且**不按业务日**过滤），而生成的编号 `HP<yyyyMMdd><seq(4)>`
**不含子账户维度**（`BizNoGenerator.java:37-39`）却受**全局**唯一约束 `uk_hedge_plan_no` 约束 ⇒
两个「各已含 N 条计划」的子账户在**同一业务日**取到**同一 `seq`**，编号相撞，第二个写入被拒。
对照：实货敞口编号 `BizNoGenerator.exposure(...)` **显式含子账户 ID**（`BizNoGenerator.java:134-146`），故其「按子账户计数」是自洽的——**套保计划编号沿用了敞口的计数口径，但遗漏了子账户维度**。

**既有绿测为何未挡**：`PlanServiceTest` 等以**假 DAO**驱动（`count` 返回固定值、唯一约束不强制），
`M1Dm8EquivalentIntegrationTest` 未覆盖「跨子账户 × 同日」编制 ⇒ 该缺陷在「单子账户」视角下不可见。

## 影响面

- **功能**：任何「**两个及以上子账户在同一天各自编制套保计划**」的场景，**第二个必失败**；
  而这**正是 `PROJECT.md` §9 M1 验收方式的第一句**（创建两个子账户→各自产出套保计划）⇒ **M1 验收 1 直接阻断**。
- **数据一致性**：失败发生在计划行插入处（同事务），本次不落库；但请求返回 `10022 内部错误`，
  **未按 `UNIQUE_CONFLICT(10010)` 语义返回**，且 `BizNoGenerator.retryOnUniqueConflict`（§3.5「冲突重试最多 3 次」）
  **在 `createPlan` 未被接线** ⇒ 即便重试也不会成功（`seq` 是确定性取值），且错误码对调用方不可判读。
- **规避**：无合规规避手段。改业务日可绕（不同日期 `HP<日>` 前缀不同），但**违背验收场景**（两子账户应能同日各建计划）；
  手工干预编号不可行（`uk_hedge_plan_no` + 编号由应用层生成）。

> **修复方向建议（供参考，不代开发定方案）**：使 `seq` 与编号的唯一性域一致——如取**全局当日序号**（`count` 去掉子账户过滤、按业务日过滤），
> 或令编号**含子账户维度**；并将插入经 `BizNoGenerator.retryOnUniqueConflict`（§3.5，最多 3 次）以吸收并发下的偶发冲突；
> 同时**补一条「跨子账户 × 同日各建计划 ⇒ 皆成功且 `plan_no` 互异」**反退化用例（现无守卫，故本缺陷得以逃逸）。
> 是否采用及具体口径由责任开发 + 技术负责人裁定。
