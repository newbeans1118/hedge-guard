## 3. §4.4 二十条规则 —— 可验证性判定表

> **判定标准**：**可验证** = 能给出**唯一确定判据**、用例可构造、结果可客观观测；**需补充说明** = 可测但**判据/取数口径未写死**，当前无法构造确定性用例；**不可验证需改造** = 结构上无法观测。

| # | 规则 | 判定 | 判据（可构造用例） | 缺口 / 建议 |
|---|------|:----:|------|------|
| 1 | 借贷平衡 `SUM(借方)=SUM(贷方)` | ✅ 可验证 | 构造借贷差 1 分钱的分录 → 提交后**拒绝且整单回滚**（查 `t_voucher` 无该单、`t_voucher_line` 无孤儿行） | 判据清晰；`t_voucher.total_amount` 可作为冗余校验点 |
| 2 | 计划数量 ≤ 敞口未覆盖数量 | ✅ 可验证 | 敞口未覆盖量 Q：提交 `Q` → 通过；提交 `Q+0.0001` → 拒绝 | 需写死"未覆盖量 = `exposure_qty − covered_qty`"及**取数时点**（对应 `snapshot_time`） |
| 3 | `SUM(交易计划数量) ≤ 套保计划数量` | ✅ 可验证 | 合计 == 计划量 → 通过；合计 > 计划量 → 拒绝 | 需写死**单位口径**（手 vs 折算实物量），建议强制折算后比较 |
| 4 | `Σ 子账户 = 真实账户` | ✅ 可验证 | ① 一致 → `result='CONSISTENT'`；② 人为改一个子账户持仓 → `INCONSISTENT_BLOCKED` 且 `block_effective_time` 非空 | 与 G-6 联动：差异归属须结构化 |
| 5 | 岗位分离互斥 | ✅ 可验证 | 两两互斥组合穷举（`t_position_conflict` 矩阵）：授予互斥角色 → 拒绝，并记 `t_unauthorized_attempt` | C++ `0x100E` 兜底可再验一层 |
| 6 | 三方核对 `p1≠p2≠p3` | ✅ 可验证 | 同一账号充当两方签署 → 第二签被拒（`uk_check_signature_task_role` + 角色比对） | 与 G-4 联动 |
| 7 | "日期不得晚于当日" | ✅ 可验证 | 注入 `Clock`=D，录 D+1 → 拒绝（`NFR-TEST-4` 可注入时钟） | 须写死"当日"取自**业务日期**而非 DB `CURRENT_DATE` |
| 8 | 额度不得跨品种/跨子账户串用 | ✅ 可验证 | 用 A 品种额度给 B 品种下单 → 拒绝（C++ `0x1004`/`0x1005`/`0x1017`） | — |
| 9 | 敞口状态由引用关系自动计算 | ✅ 可验证 | 计划驳回/终止后 → 敞口由 `COVERED` 回退至 `PARTIALLY_COVERED`/`PENDING_HEDGE`，且 `covered_qty` 回退 | — |

## 5. §4.6 子账户贯穿与"可加总" —— 独立复核

### 5.1 本席独立结论

| 复核项 | 本席判定 | 依据 |
|--------|---------|------|
| 五类数据 `sub_account_id` 是否**行级**携带、可 `GROUP BY` 直接求和 | ✅ **成立** | 43 张 `NOT NULL` 表均在行级携带，**无一依赖 join 推导**；连接/明细表（`t_hedge_plan_exposure`、`t_exposure_detail`、`t_production_plan_line`、`t_voucher_line`）**均冗余携带** |
| 是否**遗漏**子账户标识 | ✅ **无遗漏**（五类 56 张逐表核对通过） | 8 张可空、5 张不适用**均有书面理由**（E1 外部基准 / E2 全局期间 / E3 组件重放），理由成立 |
| "**可加总**"是**结构要求**而非实现约定 | ✅ **成立** | ① 明细自带标识（非"用户→子账户"或"计划→子账户"推导）；② **不落"持仓汇总表"**，汇总用视图/聚合（`Σ明细≡汇总`天然成立）；③ `t_aggregate_check` 的 `sum_sub_account` 与 `real_account_value` 分列存储，与外部基准（`t_ctp_settle_*`，E1 合并数据）可对拍 |
| v1.1 新增 3 张表是否改变结论 | ✅ **不改变** | `t_sub_instrument_quota`（层②，`NOT NULL`）、`t_annual_scale`（子账户口径 `NOT NULL` / 全账户口径可空，E5）、`t_check_signature`（流程维，范围标注）；三者均未破坏"五类行级可加总" |

### 5.2 对技术负责人"43 张 NOT NULL、无需求 join"的**独立复核**

- **"43 张 `NOT NULL`"**：本席重算 = 敞口11 + 计划7 + 交易7 + 持仓4 + 资金7 + 凭证7 = **43**，**与 §4.6.2 一致**；但文档 §4.6.4 写 40（G-1）→ **结论数字须以 43 为准**。
- **"无需求 join 即可求和"**：**成立**——43 张均为行级列，`SELECT sub_account_id, SUM(<度量>) FROM <表> GROUP BY sub_account_id` 即可，无需 join。
- **但需注意三处口径**，否则"求和"会出错：
  1. **可空作用域表的求和会漏账户级行**：`t_fund_quota`（`quota_scope='ACCOUNT'` 时 `sub_account_id=NULL`）、`t_stress_test`（NULL=全账户）、`t_annual_scale`（`TOTAL_ACCOUNT`）、`t_product_quota` 层③——对它们 `GROUP BY sub_account_id` 会**丢弃账户级行**，须按 `scope_type`/`limit_layer` **分别聚合**；
  2. **加总对账只应取"核心三表"**：持仓 `t_settle_position` / 资金 `t_settle_fund` / 盈亏 `t_settle_pnl`、以及 `t_fund_ledger`——它们才与 CTP 真实账户**同口径**；
  3. **单位须先经 `t_product_unit.convert_factor` 折算**，否则跨品种求和无意义（§3.2 已声明，须在用例前置条件中落实）。
- **补充确认（优点）**：加总阻断到 C++ 交易路径的下发通道**存在**——`CMD_SET_TRADING_SUSPEND`（`0x0118`，`scope=OPEN_ONLY`，`sub_account_id=0` 表全账户）。故"阻断期间新开仓被拒、平仓放行"在**全内存路径上可实现**，测试点成立。

> **本席结论**：技术负责人关于"可加总为结构要求"的**实质结论成立**；但其**自评的两个汇总数字不自洽**（40 vs 43）且 §4.6.3 的"不携带"计数不可核验，故该结论**目前不可仅凭文档复现**——须按 B/G 项修复后方可作为门禁证据。
