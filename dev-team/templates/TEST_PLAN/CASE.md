# 测试用例

> 负责人：测试经理 ｜ 阶段：S5 ｜ 版本：v0.1

- **项目**：
- **用例编号**：`TC-<模块代号>-<序号>`（须与 `TEST_PLAN/INDEX.md` §2 用例总表一致）
- **归属文件**：`docs/TEST_PLAN/<模块代号>.md`
- **编写人**：测试经理
- **编写时间**：

> 📁 **本文件的用途**：承载**单条用例的完整定义**。
>
> **什么时候需要独立成文**：
>
> | 情形 | 用法 |
> |------|------|
> | 用例量少 | **不必建文件**——直接在 `TEST_PLAN/<模块代号>.md` 里按本结构写 |
> | 用例数量多、单条逻辑复杂 | 一条用例一份文件：`docs/TEST_PLAN/cases/TC-<模块>-<序号>.md` |
> | 需要给执行者单独下发 | 把本文件填好后作为工单附件 |
>
> 换言之：**本模板是"一条用例该有什么"的规范**，`TEST_PLAN/<模块代号>.md` 是它的批量容器。
> 两者字段必须一致——不得一处多、一处少。

> ⚠️ **本模板定义的是「模块内用例」**。三类用例**不在模块文件里**，各有归属：
> 边界值 → `BOUNDARY.md`（`TC-BOUND-*`）；异常路径 → `BOUNDARY.md`（`TC-EXC-*`）；
> 非功能（性能/安全/可靠性/兼容/易用/可部署/可维护/可测试）→ `NONFUNCTIONAL.md`
> （`TC-<类别>-*`）。**不要**把这三类写进模块文件，否则编号与文件归属会自相矛盾。

## 附：写法示例与反例

### 示例（合格）

```markdown
## 1. 用例基本信息

| 项 | 内容 |
|----|------|
| 用例编号 | `TC-AUTH-1` |
| 用例标题 | 正确凭据登录返回有效凭证 |
| 所属模块 | `AUTH` |
| 用例类型 | 功能 |
| 优先级 | P0 |
| 设计方法 | 场景法 |
| 自动化 | 可自动化 |

## 2. 追溯

| 项 | 内容 |
|----|------|
| 对应需求 | `FR-AUTH-1 @ REQUIREMENTS/AUTH.md` |
| 对应业务流程 | 用户每日登录 |

## 3. 前置条件

| 类型 | 内容 |
|------|------|
| 数据 | 已存在有效账户 `demo01` / 口令 `Test@1234`，账户状态为启用 |

## 4. 测试步骤

| 步 | 操作 | 输入数据 |
|----|------|---------|
| 1 | 调用登录接口 | `username=demo01, password=Test@1234` |
| 2 | 检查响应 | — |

## 5. 预期结果

| 步 | 预期结果 | 判定方式 |
|----|---------|---------|
| 1 | 返回 HTTP 200，响应体 `code=0` | 查返回值 |
| 2 | 响应体含非空 token，有效期 7200 秒 | 查返回值 |
```

### 反例对照

| ❌ 不合格写法 | 问题 |
|-------------|------|
| 标题"测试登录功能" | 没说验证什么——是验证成功？失败？还是账号锁定？ |
| 前置条件"系统已部署" | 无法构造：部署到哪个环境？用什么数据？ |
| 步骤"登录系统" | 粒度太粗：一步里含输入、提交、跳转三个可观察结果 |
| 预期"登录成功" | 不可判定：怎么知道成功了？看什么？ |
| 无「对应需求」 | 追溯断裂——这条用例为什么存在？ |
