## 填写总则

> 本节是给**编排者**的指引：如何协助用户把这份文件写到位。

| 原则 | 说明 |
|------|------|
| **逐项确认，不代替用户拍板** | 编排者负责提问、给出选项、提示后果；最终选择由用户决定 |
| **不确定就问，不猜** | 宁可多问一轮，也不要写入未经确认的假设——被假设的内容会一路传导到代码 |
| **具体到可执行** | 每项都要写到"执行者照着做不会产生歧义"的粒度 |
| **边界优先** | §4.2「明确排除」比「包含」更能省返工，写不出排除项说明范围还没想清 |
| **可验证** | §10 成功标准必须是能观测的事实，不能是主观感受 |

**编排者的提问顺序**：§1 目标 → §3 用户 → §4 范围 → §5 技术栈 → §6 约束 → §7 交付深度。
其中 §5 必须先问清——它是唯一事实源，未确认不得开工（见编排规则 §11.1）。

## 5. 技术栈

> ⚠️ **本节是技术栈的唯一事实源。** 后端 / 前端 / 测试角色均按此表工作。
>
> **合格标准**：每项具体到「名字 + 版本/规格」，执行者照着做不会产生歧义。
> 本套件**不预设任何技术栈**——选什么由项目决定，此处必须由用户明确。

| 项 | 选择 | 说明 |
|----|------|------|
| 语言与版本 | | 须带版本号，如 `Python 3.11` / `C++11` / `Go 1.22` |
| 框架 / 库 | | 如 `FastAPI 0.104`；无框架写「仅标准库」 |
| 构建 / 包管理 | | 如 `pip + requirements.txt` / `CMake` / `go mod` |
| 测试框架 | | 如 `pytest` / `ctest` / `go test` |
| 前端 | | 如 `React 18 + Vite`；无前端写「无」 |
| 运行环境 | | 如 `Ubuntu 22.04` / 浏览器版本要求 |
| 依赖策略 | | 如「最小依赖，引入需在架构文档论证」 |

**常见不合格写法**：

- ❌「用 Python」——缺版本，Python 2 和 3.11 差异足以让产出作废
- ❌「前端用个框架」——缺具体技术名，前端工程师只能猜
- ❌ 留空——**留空则不得开工**，须回到本轮补全（见编排规则 §11.1）

**若项目有既有技术栈约束**（如团队统一要求、线上环境限制），在此注明来源与理由。

## 10. 成功标准

> **合格标准**：写成**能观测的事实**，每条都给出验证方式。
> 至少一条须是「用户能实际跑通的端到端场景」。
>
> 这一节决定「项目做没做成」，最容易被写空——请认真对待。

| # | 成功标准 | 验证方式 |
|---|---------|---------|
| 1 | | 如：`pytest` 全部通过，覆盖率 ≥ 80% |
| 2 | | 如：用户按 README 三步内跑通完整流程 |
| 3 | | 如：关键接口 P95 延迟 < 200ms |

**常见不合格写法**：

- ❌「运行流畅」——无法验证
- ❌「用户体验良好」——无观测指标
- ❌「代码质量高」——无判定标准
- ✅「新用户不看文档，5 分钟内能完成首次下单」
